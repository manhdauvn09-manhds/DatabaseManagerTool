1. Nguyên nhân gốc — tại sao 4 Harness bị chấm thấp

Phát hiện xuyên suốt (root cause chung): theo nguyên tắc C10 (honest enforcement), các mục policy khai enforced_at: gateway (H2, H5) và enforced_at: workflow_engine (H7) chỉ là tuyên bố — gateway PDP và workflow engine chưa live, nên scorer chấm là "declared-not-enforced" → điểm thấp dù policy đã viết đầy đủ.

Riêng H3: scorer chỉ đếm regression_suites_required = 3 suite của chính harness (policy-ci, red-team, golden). 236 test thật của SecureConnect hoàn toàn vô hình với H3. Chính comment trong casan-policies.yaml.new đã thừa nhận: "their actual test count (3400+ tests) was invisible to H3 until they added a fourth entry" → đây là lỗi thiết kế common của ToolKit.

2. Việc DỰ ÁN cần làm (project-side)

H3 — Evaluation (tác động lớn nhất, làm trước)

  1. Đăng ký test suite thật của SecureConnect vào casan-policies.yaml:
evaluation:
  regression_suites_required:
    - "policy-ci"
    - "red-team"
    - "golden"
    - "secureconnect-unit"          # ← THÊM
  suite_commands:
    policy-ci: "python .harness/scripts/lib/harness_policy_check.py ."
    red-team:  "python .harness/scripts/lib/harness_redteam.py ."
    golden:    "python .harness/scripts/lib/harness_golden.py ."
    secureconnect-unit: "npm test --silent --prefix SecureConnect"   # ← THÊM
  1. Bổ sung golden dataset domain-level vào .harness/eval/golden/golden-cases.jsonl: các case SSRF guard, sqlValidator deny-list, CSRF origin check, mutate cap — hiện golden chỉ cover deny-policy của harness, chưa cover nghiệp vụ app.
  2. Kết nối judge-rubric: dùng .harness/eval/judge/judge-rubric.md làm tiêu chí cho agent review (mục 4) để feedback loop từ test fail quay lại spec.

Kỳ vọng H3 tăng mạnh ngay: từ "zero tests" → suite thật 236 tests được tính + gate release.

H2 — Tool

  1. Bật audit per-call local — đã có sẵn. harness-post-tool-use.ps1 đã append mỗi tool call (input/output hash, agent, session) vào ledger. Không cần làm gì.
  2. Idempotency key ✅ ĐÃ LÀM (không đặt trong push-and-deploy.ps1 như dự kiến ban đầu — script đó chỉ push, deploy đi qua MCP tool nên phải làm ở tầng hook): idempotency-checkpoint.ps1 (PreToolUse) + idempotency-record.ps1 (PostToolUse) + lib-idempotency.ps1. Key = sha256(tool + input), TTL 1h. Chỉ ghi lần chạy THÀNH CÔNG nên retry sau lỗi không bị chặn oan.
  3. Rate limit local ✅ ĐÃ LÀM: cùng hook trên, đếm cửa sổ trượt theo tool.rate_limits (deploy 6/giờ, http_fetch 30/phút…), vượt ngưỡng → ask + ghi ledger.
  4. Giới hạn trung thực (C10): hook chỉ trả được ask — nó không trả được kết quả cache thay cho tool. Đây là "phát hiện + chặn để người quyết định", chưa phải idempotency tuyệt đối như gateway PDP làm được.

H5 — Governance

  1. Khởi tạo hash-chain ledger — không cần làm. Kiểm chứng ngày 2026-08-03: ledger writer đã ship và hoạt động, tự tạo chain khi append đầu tiên; evidence-ledger.ps1 verify báo LEDGER INTACT. Audit per-call cũng đã được nối sẵn trong PostToolUse.
  2. Approval checkpoint local ✅ ĐÃ LÀM: .harness/scripts/powershell/approval-checkpoint.ps1 — đọc governance.approval_required (C2, không hardcode), trả permissionDecision: "ask" cho deploy/rollback_deploy/mysql_query (chỉ WRITE)/provider_key_rotate, ghi entry type: approval vào ledger trước khi hỏi. Nối vào PreToolUse sau runtime-guard.
  3. Risk registry sống: risk-registry.yaml đã có — bổ sung entry cho các action của dự án (bulk mutate, recreate volume ❌, nginx script ❌ theo CLAUDE.md) để policy engine đọc được.
  4. Compliance report tháng ✅ ĐÃ LÀM: compliance-report.ps1 — verify hash-chain trước khi báo cáo (chain hỏng thì báo cáo vô nghĩa), rồi tổng hợp ai-làm-gì, approval, deny, incident rủi ro cao, top tool, chi phí token → docs/compliance-YYYYMM.md.
  5. Nightly full-suite ✅ ĐÃ LÀM: nightly-regression.ps1 — chạy cả 4 suite (55s thực đo), fail thì ghi incident test_regression_after_pass và chỉ ra cần bổ sung file nào vào core_files.

H7 — Orchestration

  1. Định nghĩa DAG pipeline cụ thể cho luồng đối ứng (chính là hệ agent ở mục 4): Scope → Review → Fix → Test → Gate → Deploy, khai trong file workflow (vd .claude/workflows/change-pipeline.md hoặc Workflow script) để scorer thấy DAG thực.
  2. Retry có giới hạn + BACK-TO-PLAN: fix agent tối đa 3 vòng, quá → dừng, báo người.
  3. Transaction boundary thực ✅ ĐÃ LÀM: deploy-verify.ps1 (PostToolUse) — deploy xong tự smoke check /api/health (3 lần thử, cách 5s), fail → trả decision: "block" kèm hướng dẫn rollback bắt buộc + ghi incident risk_level: critical vào ledger. Config (URL, chuỗi mong đợi, retry) nằm trong orchestration.transaction.* — C2, không hardcode.
  4. Giới hạn trung thực (C10): hook phát hiện và chặn, nhưng không tự gọi được rollback_deploy (hook không có quyền gọi MCP tool). Việc rollback vẫn do agent/người thực hiện sau khi đọc cảnh báo. Đây chưa phải auto-rollback đầy đủ.
  5. Model fallback — chưa làm, cần workflow engine (xem request ToolKit #4).
  6. Model fallback: dùng chính ladder đã khai trong policy khi spawn agent (review → opus, fail → haiku).

4. Hệ Agent tự động Review → Fix → Test (impact-based, không test all)

4.1 Kiến trúc pipeline

 git diff ──► [A1 Scope Agent] ──► impacted-map (files + modules + test liên quan)
                    │
                    ▼
             [A2 Review Agent] ◄──── judge-rubric.md (H3)
              │ APPROVED?│
              │          └─ REJECTED ──► [A3 Fix Agent] ── max 3 vòng ──► quay lại A2
              ▼                              (quá 3 vòng → dừng, báo người)
             [A4 Test Agent]
              ├─ UT:  jest --findRelatedTests <changed files>   ← CHỈ vùng ảnh hưởng
              ├─ IT:  chạy test của route/module trong impacted-map
              └─ Full suite: CHỈ khi (a) đổi file core dùng chung ≥N nơi, (b) trước deploy
                    │
                    ▼
             [A5 Gate] ─ pass ─► approval (H5) ─► deploy ─ fail ─► rollback_deploy (H7)
                    └─ ghi toàn bộ vào ledger chain.jsonl (H2/H5)

4.2 Chi tiết từng agent

AgentNhiệm vụCách xác định "vùng ảnh hưởng"
A1 Scope
Explore/haiku		Từ git diff --name-only dựng impacted-map① jest --findRelatedTests (dependency graph có sẵn của Jest) ② import graph bằng madge cho reverse-deps ③ map route API → test IT tương ứng (bảng cố định trong file config)

opus, effort high		LLM-as-judge theo judge-rubric.md: correctness, security (OWASP), quy ước CLAUDE.md. Verdict APPROVED / CHANGES_REQUIRED / REJECTED + scoreChỉ đọc files trong impacted-map + reverse-deps cấp 1 — không quét cả repo
A3 Fix
sonnet		Nhận findings CONFIRMED từ A2, sửa từng finding, không mở rộng scopeChỉ sửa file bị nêu trong finding; mỗi vòng fix xong trả lại A2 re-review đúng phần sửa
A4 Test
haiku, effort low		Chạy test theo tầng, dừng sớm khi failUT vùng ảnh hưởng → IT module → full suite chỉ khi chạm file "core" (danh sách: store.ts, dbConnector.ts, route-helper.ts, ssrfGuard.ts, serverVault.ts…) hoặc trước deploy
A5 Gate
script, không cần LLM		Tổng hợp verdict + test result → xin approval người (AskUserQuestion) → deploy → smoke check → fail thì rollback. Append tất cả vào ledger—

4.3 Quy tắc "chỉ test vùng ảnh hưởng"

  • Tầng 1 (luôn chạy, ~giây): npx jest --findRelatedTests $(git diff --name-only HEAD -- 'SecureConnect/src/**/*.ts') — Jest tự lần dependency graph, chỉ chạy test import (trực tiếp/gián tiếp) file đã đổi.
  • Tầng 2 (khi đổi API route): chạy test của module tương ứng (map src/app/api/db/[id]/rows/ → mutate.test.ts, store.test.ts…).
  • Tầng 3 (full 236 tests): chỉ khi (a) file core-shared thay đổi, (b) đổi package.json/config build, (c) bước Gate trước deploy — vì Dockerfile đã có test gate, full suite chạy 1 lần duy nhất trong build.
  • Chống lọt lưới: nightly cron chạy full suite 1 lần/ngày — nếu fail mà các lần impact-test đều pass → ghi incident test_regression_after_pass (đúng hallucination flag H6 đã khai) và mở rộng danh sách core files.
